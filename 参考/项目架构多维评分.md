# EUI-NEO 项目架构多维评分

评估日期：2026-08-03

评估范围：当前 dev 分支，在完成 Runtime 职责拆分与通用按键事件模型之后。评分依据是源码边界、修改扇出、四种后端组合的实际构建与测试结果，不以文件数量单独判断架构好坏。

## 结论

综合评分：**8.2 / 10**

当前架构不属于“过度复杂到难以维护”，但仍是一个能力密集、编译耦合偏高的 header-heavy UI Runtime。此次调整解决了两个最明显的问题：

- Runtime 不再直接拥有 primitive 实例映射、GPU 资源释放循环和渲染递归。
- 输入模型不再为每个按键增加一个 bool 字段，新增按键不需要修改输入队列消费逻辑和文本组件事件结构。

复杂度现在主要来自 UI Runtime 本身需要协调布局、命中测试、动画、脏区与生命周期，而不是来自无意义的小文件或胶水层。

## 本次改进的实际影响

### Runtime

调整前，Runtime 同时声明并持有十余个实例 map、资源释放流程和全部渲染递归方法。文件虽然按主题拆分，所有权仍集中在同一个类。

调整后：

- runtime::InstanceStore 统一拥有 Rect、Polygon、Text、Image、ShaderToy、交互、布局、滚动、滑块、计时器、paint bounds 和 retained layer 状态。
- InstanceStore 自己处理创建、seen/prune、资源释放、clear 和实例派生的 render transform。
- RuntimeRenderer 直接依赖 Ui 与 InstanceStore，拥有 14 个渲染相关方法。
- Runtime 只在渲染入口构造 RuntimeRenderer 并调用 renderDirect，没有为每个方法编写转发胶水。

这不是把巨型类机械地换个名字，而是迁移了状态所有权和完整行为闭环。

### 输入模型

调整前，每增加一个按键通常会扩散到枚举、队列 bool、消费拷贝、两个后端和组件判断。

调整后，输入统一为 KeyEvent，由 key、action 和 modifiers 三部分组成。KeyboardEvent 提供 findKey、hasKey 和快捷键组合查询。

新增按键仍需在两个原生后端中映射，这是平台适配的合理差异；核心队列和事件模型无需再添加字段。

## 剩余风险与建议

1. runtime_update.h 仍约 1097 行，runtime_input.h 约 551 行。它们共享树遍历、交互状态和脏区语义，当前不宜继续强拆；只有出现稳定、独立的状态所有权时才应再提取。
2. runtime_render.h 约 846 行，但现在由单一渲染职责支撑，文件较长本身不是拆分理由。若未来 primitive 种类显著增加，可按“遍历/retained layer”和“primitive drawing”两个真实边界再评估。
3. runtime_instances.h 约 501 行，同时包含实例类型和 store。两者高度内聚且只服务 Runtime，目前合并比新增一个小头文件更易维护。
4. Header-heavy 结构会造成 Runtime 修改后大量示例重编译。若构建时间成为持续痛点，应优先把稳定实现迁到 .cpp，而不是继续增加更多 header 分片。
5. 通用按键事件目前只建模 Press 与 Repeat，因为现有业务不消费 Release。只有出现真实释放事件需求时再扩展，避免预先增加无用状态。

## 最终判断

项目当前的复杂度大部分是功能复杂度，不是文件拆分制造的复杂度。维护体验已从“状态和行为都集中在 Runtime、按键修改四处扩散”改善为“所有权位置明确、后端只负责映射、核心只处理统一事件”。

不建议继续以减少文件数为目标清理 core/runtime/runtime_*.h。下一阶段若要继续提高评分，应以降低 header 编译耦合、补充 Runtime 边界文档和针对输入队列的无窗口测试为主，而不是再造 Manager、Service 或转发层。
